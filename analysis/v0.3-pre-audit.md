## 作業1: 末尾再帰の保証（proper tail call の定数スタック実行）

### 現状分析

**SPEC 側の末尾位置の定義**
- §7.3「末尾位置制限」: `Do` は以下の位置にのみ現れてよい — 関数本体の最上位、let 本体、if/when の then/else（両方）、match の各アームの末尾、cond の各節と `:else`。式の中に `Do` は現れない（MUST）。
- §8.5「再帰」: 末尾呼び出しの最適化は **SHOULD**（JS バックエンドではループ変換）。非末尾再帰のスタック制限は実装依存で、Rust 実装は上限を定め超過時に internal-error 診断を返す。

**Core IR 上の末尾位置（§5 の構造 + §4 の脱糖規則から導出される完全な列挙）**

末尾位置（その位置にある式の評価が「呼び出し元のフレームを消費しない」対象）:
1. `Lam.body` — 関数本体の末尾。`App` がここにあれば末尾呼び出し。
2. `Let.body` — let 本体の末尾（`Let.rhs` は**非**末尾）。
3. `If.then` / `If.else_` — 両枝が末尾。`when` は `If(c,e,nil)`、`cond` はネストした `If`、`and/or` は `If`/`Let` に脱糖される（§4）ので、それらの各アーム末尾もここに帰着する。
4. `Match` の各アームの `body`（scrutinee は**非**末尾）。
5. `Do.body` — do 本体の末尾（各 bind の `expr` は**非**末尾）。

末尾ではない位置（被演算子を含む）:
- `App.f` と `App.args[*]` — 関数・引数の各被演算子は末尾ではない。特に `(-> x f g)` = `App(g, [App(f, [x])])` では内側の `App` は引数なので非末尾。
- `Let.rhs`、`If.cond`、`Match.scrutinee`、`Obj` の各フィールド値、`Field.obj`、`Do` の各 bind `expr`。

**実装側の現状**
- インタープリタ（src/eval.rs）: **TCO は未実装**。`eval_core`（eval.rs:282）は素直な再帰評価で、`Core::App`（eval.rs:296-303）は `interp.apply` を呼び、`apply`（eval.rs:36）が `depth += 1` して `MAX_CALL_DEPTH = 10000`（eval.rs:11）を超えると internal-error を返す（eval.rs:47-55）。末尾位置の `App` も例外なくフレームを消費する（Rust スタックも深さカウンタも）。テスト `recursion_depth_limit_is_internal_error`（eval.rs:774-789）は 256MB スレッド上で `deep-add.lts` の `add-money(20000)` が internal-error になることを検証している。
- 大域脱出（do の早期リターン）: `Core::Do` の bind 評価で `Err` を検出すると `return Ok(v)`（eval.rs:359-365）する**値レベルの短路**。`Do` が末尾位置に限定されている（§7.3。実際には型検査で `Do` の型が `Result` と unify されることで非末尾の `Do` は type-mismatch になる — check.rs:616, 760, 779-830）ため、`Err` は末尾のフレームを素通りして最寄りの `Do` bind または関数境界まで正しく伝播する。TCO（trampoline 化）と直交しており、両立する。
- JS バックエンド（src/emit.rs）: 末尾位置は `stmt()` が `return expr;` として出力（emit.rs:454-487）、`Do` は `if (r.tag === "Err") return r;` の早期リターン（do_stmt, emit.rs:489-504）。しかし `Core::App` は平坦な `f(args)` 呼び出し（emit.rs:613-660）で、**ループ変換もトランポリンも未実装**。V8 は PTC 非搭載なので、現状では末尾再帰も JS スタックを消費し RangeError になる（§8.5 の SHOULD「ループ変換」は未達）。

### 「proper tail call は定数スタックで実行される」を導入した場合の影響評価

- **JS バックエンド**: 直接自己末尾再帰（`return f(...)` で f が現在の関数）はコンパイル時に検出でき、`while` ループ化すれば生成コード品質は良好（余分なフレーム・thunk なし）。相互再帰や間接呼び出し（クロージャ変数経由）はトランポリン化（thunk を返してトップレベルのドライバループで消費）が必要で、呼び出しごとのアロケーション増と生成コードの複雑化を伴う。いずれにせよ §8.5 の SHOULD が MUST になるには実装が前提。
- **WASM**: tail-call proposal の `return_call` / `return_call_indirect` にそのまま対応する。将来の P4 バックエンドにとって「定数スタック」の約束は自然な射影であり、この約束があるからこそ WASM 化が意味論保存になる。
- **インタープリタ**: `eval_core` を trampoline 化（`App` をループで回し、末尾位置ではフレームを再利用）すれば末尾呼び出しは定数スタックになる。`depth` カウンタは非末尾呼び出しにのみ適用。`calls` 統計（eval.rs:52-54）は維持可能。大域脱出（`Do` の `Err` 短路）は値返しなので trampoline と衝突しない。

### 選択肢の比較

| 選択肢 | 意味論的帰結 | 実装コスト | 備考 |
|---|---|---|---|
| (A) 現状維持（§8.5 は SHOULD のまま） | 末尾再帰の深さ上限はバックエンド依存（JS: RangeError、interp: internal-error）で仕様上許容。バックエンド交換時に観測差が出る | なし | バックエンド交換の「意味論を変えない」という目的に反する |
| (B) MUST「proper tail call は定数スタックで実行される」を導入 | 全バックエンドで深い末尾再帰が成功することが保証される。非末尾再帰の上限は実装依存のまま | 中（interp の trampoline 化 + emit の自己再帰ループ化・相互トランポリン） | WASM `return_call` と自然に対応 |
| (C) SHOULD のまま + 「上限超過は §8.6 の実行時エラーであり internal-error ではない」と明確化のみ | internal-error（バグ扱い）と runtime error（仕様上の振る舞い）の区別が明確になる | 小 | 保証そのものは導入しない |

### 推奨案と理由

**(B) を v0.3 で導入する。** 理由: 本マイルストーンの目的が「バックエンド交換で意味論を変えない」ことであり、末尾呼び出しのスタック挙動はバックエンド間で最も観測されやすい差の一つであること。JS でもループ変換+トランポリンで実現可能、WASM では `return_call` に直結、interp でも trampoline で実現可能なので、MUST として課せるに足る。非末尾再帰のスタック上限は引き続き実装依存（§8.5 既定どおり）。

## 作業2: 数値の意味論（JS number = f64 への暗黙依存の棚卸し）

### 現状分析（f64 暗黙依存箇所の完全な棚卸し）

- **字句（リテラル）**: SPEC §2.3 `number ::= /-?[0-9]+(\.[0-9]+)?([eE][+-]?[0-9]+)?/`。実装 lexer.rs:202-238 `lex_number` はこの正規表現どおりに走査し `text.parse::<f64>()`（lexer.rs:234）で変換。Rust の `f64::from_str` は正しく丸められた10進→binary64変換であり JS の `Number()` と同一。オーバーフロー（例 `1e999`）は Rust parse が `Ok(inf)` を返すため `Infinity` となり JS と一致。16進・0b/0o リテラルは存在しない。トークンは `TokenValue::Num(f64)`（token.rs:75）、AST は `LitValue::Num(f64)`（parser.rs:1221-1227）。
- **型**: `Type::Number` 単一（types.rs）。整数型は存在しない。
- **値**: `Value::Num(f64)`（value.rs:9-10）。
- **演算**: インタープリタは apply_builtin（eval.rs:127-141）で `+ - * / < > <= >= mod abs min max` をすべて f64/IEEE754 演算として直接実行。`/ 1 0` → Infinity、`/ 0 0` → NaN はテスト済み（eval.rs:748-755）。JS 側は emit.rs:338-372 `stdlib_impl` で `a+b`、`a%b`、`Math.abs`、`Math.min/max` 等に射影。
- **比較・等価**: `<` 等は f64 比較。`=` は structural_equal 経由で `Num` は `x == y`（value.rs:114-117）。NaN≠NaN、-0==+0 は Rust `==` と JS `===` で一致。
- **JSON 診断・出力への数値直列化**: `Diagnostic.data` は現状 path/型文字列のみで生の数値を含まない（diagnostic.rs）。ただし `Value` は Serialize 済みで、ゴールデン IR スナップショット（tests/golden/*.json の `Lit`）では serde_json（ryu）により f64 が直列化され、決定性は ryu が担保する。REPL の `test` 応答は `print_value`（文字列）経由（repl.rs:125-129）。T7 の JS 側比較は JSON.parse 後の値比較なので、ryu の `1e21` と `JSON.stringify` の `1e+21` という表記差は吸収される。

**付録C #4「数値演算で自然に一致」に反する現実の食い違い（実装バグ候補・仕様変更ではない）**:
1. `min`/`max` の NaN: JS `Math.min(NaN,1)=NaN` に対し Rust `f64::min(NaN,1.0)=1.0`（非 NaN 側を返す）→ 不一致。
2. `len`: Rust は `chars().count()`（Unicode スカラ値数）vs JS `s.length`（UTF-16 コード単位数）→ 非BMP 文字（絵文字等）で不一致。
3. `str-slice`/`slice` の添字: Rust は char 数ベースの `js_slice_bounds`（eval.rs:267-281）、JS は UTF-16 単位の `slice` → 非BMP で不一致。
4. `str`（数値→文字列）: Rust `print_value` は f64 の Display（指数表記を使わない、`-0` は `"-0"`）vs JS `String(a)`（`1e21` は `"1e+21"`、`-0` は `"0"`）→ 不一致。
5. `nth` の小数添字: Rust は `i >= 0.0 && (i as usize) < len` で切り捨てて `ok(arr[1])`、JS は `arr[1.5]` = undefined を `ok(undefined)` で包む（undefined は存在してはならない §8.2 MUST）→ 不一致。

### 選択肢の比較

| | (a) 全数値 IEEE754 f64 と明記（現状の成文化） | (b) Int=i64 / Float=f64 を規定 | (c) Int=i53（±2^53-1）に制限 |
|---|---|---|---|
| JS との整合 | 完全（単一表現） | i64 を BigInt で表す変換コスト大（演算ごとの分岐、`JSON.stringify` が BigInt を投げるため REPL/T7 の JSON 経路に影響） | 完全（JS 安全整数範囲内） |
| WASM/LLVM 側 | f64 のみ。整数演算の機会損失（最適化側の課題） | i64 演算が自然 | f64 のままなので整数機会は限定的 |
| 意味論の確定 | 2^53 超の丸めを「仕様上の値」として受容 | 正確な整数意味論 | 整数意味論を確定するがレンジ制約あり |
| 変更コスト | 文言のみ | 大: リテラルの int/float 分類、`/` の整数除算の定義、§11.1 の型表、`=`・比較の規則、stdlib 全演算 | 中: レンジ外のリテラル/演算結果の扱い（parse-error か実行時エラーか f64 昇格か）を新規定 |

### 推奨案と理由

**(a) を採用する。** P0〜v0.3 の安定性とバックエンド同一性（付録C #4、T7 の差分一致）を最優先し、現状を MUST として成文化する。f64 単一という約束は WASM/LLVM への射影も自明であり、「意味論を変えないバックエンド交換」の目的に最も合う。(b)/(c) は P1 の `decimal` 検討時にまとめて再評価する。あわせて上記 5 件の食い違いは仕様変更ではなく付録C #4 への違反（実装バグ）として別マイルストーンで修正する。

## 作業3: 循環構造における構造的等価 `=`

### 現状分析

- **SPEC §8.3**: `=` は構造的等価 — プリミティブは `===`（NaN は NaN と等しくない）、配列は長さと各要素の再帰的等価、obj はキー集合と各値の再帰的等価、Result は tag と value の等価。
- **Rust 実装** value.rs:114-139 `structural_equal`: Array/Obj/Ok/Err を再帰比較、Closure/Builtin は `Rc::ptr_eq`。**循環は表現不可能** — `Value` は不変ツリー（`Array(Vec<Value>)`、`Obj(BTreeMap)`、内部可変性は `Env` のみで、Closure 比較は ptr_eq で env には立ち入らない）なので、インタープリタでは `=` は常に停止する。
- **JS 実装** src/backend/runtime.js:3-17 `structuralEqual`: 同じ構造だが**循環検出なし**。循環参照を持つデータでは無限再帰し RangeError（スタック枯渇）になる。
- **P0 における循環の到達可能性**: λ LisTS P0 には代入・破壊的変更がなく、`obj`/配列は常に新規生成（`push`/`concat` はコピーを返す）なので、**純粋な P0 プログラムからは循環構造を作れない**。ただし P1 の host DI / `defn!` 完全実装でホスト側から循環構造が渡されると、JS 側ではクラッシュ、Rust 側ではそもそも表現できない、という非対称が生じる。

### 選択肢の比較

| 選択肢 | `=` の数学的性質への帰結 | 実装コスト |
|---|---|---|
| (a) 非終了を仕様として明文化 | 反射律を含む同値関係としての性質をすべて放棄。バックエンド間で「Rust では起きない / JS ではクラッシュ」という非決定性を仕様に入れることになる | なし（現状維持）だが仕様として有害 |
| (b) 循環検出で実行時エラー | P0 の到達可能領域（非循環）では現行と完全一致。`=` は到達可能な全入力で全域かつ同値関係。循環が入った場合のみ §8.6 の実行時エラー（全域性の放棄は到達不能領域に限定） | 小: JS 側は訪問ペア集合（WeakMap 等でほぼ O(n)）、Rust 側は不要（表現不可） |
| (c) 同一オブジェクト再訪で等価ショートカット（認識的/余帰納的等価） | 循環でも反射律を保持し全域。ただし合同（bisimilar）な別々の循環構造が等価になるため、`=` の意味が「構造的等価」から「余帰納的等価」へ変わる（有限非循環では三者一致） | 最大: ptr ペアの記憶と定義の追加 |

### 推奨案と理由

**(b) を採用する。** P0 では循環が到達不能なので (a)(b)(c) は観測上すべて現行と一致しており、問題は「将来 host から循環が入ったとき何が起きるか」だけである。(b) なら「止まらない」ではなく「§8.6 の実行時エラー」として定義でき、到達可能領域での `=` の全域性・同値関係性を守れる。(a) は却下。(c) は循環データが言語に正式に入る場合（P1 以降）の再検討対象。

### 修正条文の差分草案（未採用・提案のみ）

```diff
--- a/SPEC.md §8.3
+++ b/SPEC.md §8.3（草案）
 ### 8.3 等価性
 
 `=` は構造的等価とする。
+（中略）
+- **P0 では値は非循環である（循環構造を作る構文が存在しない）ため、`=` は常に停止する（MUST）**。
+- 将来の拡張（host 連携等）で循環構造が値に現れる場合、`=` は循環を検出した時点で実行時エラー（§8.6）とし、無限ループしてはならない（MUST）。
```

## 作業4: 実行時プリミティブの規範化（ok / err / structuralEqual と付録C の一致）

### 現状分析（文書と実装の両面確認）

- **export の一致**: SPEC §12.5 は runtime.js の export を `ok` / `err` / structuralEqual の**3つのみ**（MUST）と規定。実装 src/backend/runtime.js はちょうどその3つ（1-2行が ok/err、3-17行が structuralEqual）。emit.rs:21 `RUNTIME_EXPORTS = &["ok","err","structuralEqual"]` とも一致。**一致 ✓**
- **ok/err の表現**: JS `{tag:"Ok",value}` / `{tag:"Err",value}` ↔ Rust `Value::Ok(Box<Value>)` / `Value::Err(Box<Value>)`（§8.2、付録C #6）。キー順（tag→value）も一致。**一致 ✓**
- **nil ↔ null**: §8.2 で undefined は存在しない（MUST）。runtime.js は `null` のみ使用（`nth` は範囲外で null）。Rust 側 `Value::Nil`。structuralEqual は `a===null || b===null → a===b` で nil は nil とのみ等価。**一致 ✓**
- **structuralEqual の規則**: §8.3 の4規則（プリミティブ / 配列 / obj / Result）と value.rs:114-139・runtime.js:3-17 が一致。NaN≠NaN は `==`/`===` で一致。Closure は Rust で `Rc::ptr_eq`、JS では関数が最終行の `a===b`（参照等価）に落ちて一致。obj はキー集合等価（順序非依存）で一致。**一致 ✓**
- **文書側の不足（付録C と実装の差）**: (i) §8.2 の `Value` には `Builtin` バリアントが無いが、実装 value.rs:20 には stdlib 第一級関数用の `Builtin` があり、`Closure` には `name` フィールドもある（付録C の規範型に追記が必要）。(ii) `str` の実装は Rust 側 `print_value`（value.rs:141）、JS 側は emit.rs のインライン `String(a)` であり runtime.js には無い — 「3 export のみ」とは両立するが、数値→文字列の表現差（作業2の項目4）を規範化するなら §11.2 か §8.2 に `str` の規定が要る。(iii) diagnostic.rs:63-65 `to_json_line` が `unimplemented!` の死コード（呼び出し元なし）で、GUIDE.md の「ライブラリ経路でパニック禁止」に抵触しうる — 除去を別途提案（本マイルストーンでは変更しない）。(iv) §10.5 は「stdlib 関数は `$stdlib_<name>` として import する」とあるが、実装 emit.rs:326-336 は生成ファイル内に `const $stdlib_<name> = ...` として**定義**しており import ではない — 文言の微修正候補。

### 条文案（未採用・提案のみ）

§8.2 の末尾（または付録C の冒頭）に次を追加する:

```diff
--- a/SPEC.md §8.2（または付録C 冒頭）
+++ b/SPEC.md（草案）
+- **実行時意味論の規範は本節（付録C）の Rust 型定義（`Value` とその構造的等価・印字）であり、

+  射影は tag 表現（`{tag:"Ok"|"Err", value}`）、nil↔null 対応、構造的等価（§8.3）を保存しなければならない。
```
